# Limitations and what Guard does not detect

Soroban Guard is a **heuristic, syntax-level analyzer**. It parses individual
contract source files and runs a set of pattern- and structure-based checks. A
clean report means *none of the implemented checks fired* — it does **not** mean
the contract is safe. This page sets expectations and explains what the tool
cannot see.

## What Guard does not do

- **No type resolution or macro expansion.** Guard works on the source as
  written. It does not resolve types, expand macros, or evaluate `cfg`/feature
  gates, so code generated by macros or hidden behind type aliases is invisible
  to it.
- **Aliases and re-exports can defeat name matching.** Checks that match on
  identifiers (function names, storage keys, imported symbols) can be bypassed
  by `use ... as ...` aliases, glob imports, or re-exports. A renamed symbol may
  simply not be recognized.
- **Per-function, mostly intra-procedural analysis.** Most checks reason about a
  single function in isolation. Cross-function data flow, inter-contract calls,
  and whole-program invariants are largely out of scope.
- **No execution or symbolic reasoning.** Guard does not run the contract, model
  state transitions, or perform symbolic execution. It cannot prove the absence
  of a bug.
- **Not a substitute for an audit or formal verification.** Passing Guard is a
  baseline hygiene signal, not a security guarantee. High-value contracts should
  still receive a manual audit and, where warranted, formal verification.

## Where to look for what Guard cannot catch

| Class of issue | Where to look instead |
|----------------|-----------------------|
| **Logic errors** (wrong arithmetic, off-by-one, incorrect state transitions, broken invariants) | Manual review, unit/property tests, and formal verification of the core invariants. |
| **Economic attacks** (oracle manipulation, flash-loan/price manipulation, incentive misalignment, MEV) | Economic modeling, adversarial test scenarios, and review of external price/oracle dependencies. |
| **Access-control design** (who *should* be allowed to do what, role hierarchies, upgrade authority) | Threat modeling and design review of the authorization model — Guard only flags known syntactic patterns, not whether the policy is correct. |
| **Cross-contract and integration risks** | Integration tests against real dependencies and review of the interfaces you call. |
| **Macro-generated or aliased code paths** | Review the expanded/generated code directly; Guard sees only the source as written. |

## Reporting gaps

If you believe Guard missed something it *claims* to detect, that is a bug —
please open a regular GitHub issue with a minimal reproduction. If you are
unsure whether a finding is in scope, see [`SECURITY.md`](../SECURITY.md).
